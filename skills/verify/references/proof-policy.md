# Proof

Proof names an observable result, revision and environment. Select it from the requested behavior and the project's actual surfaces. Use existing commands, drivers and platform guidance. Add [app control](../../app-control/SKILL.md) only when repeated driving lacks a capability.

## Select

For each material case, choose the cheapest check that can distinguish its failure. Trace indirect consumers: a service change can affect a browser or native client without changing either client file.

Pure logic can use focused tests; rendered interactions need observations in the relevant UI; permissions and persistence need checks at the owning operation. File extensions do not decide the test boundary. Use the project's selected test, design and component tools.

Separate component, protocol, emulator, real provider and installed-host claims. A direct call checks its contract; a running client connection checks integration; a model-driven run checks agent choices. A fixture or local emulator does not prove the real provider or host.

## Discover and retain regressions

Map material cases to actor, fixture, target, expected observation and any independent read needed to confirm a side effect. Explore selected risks when useful; documentation changes normally need no product exploration.

Treat discovered concerns as candidates. Preserve steps and observations, reproduce them with an isolated exact assertion, and distinguish a product defect from setup, locator or budget failure. After an authorized fix, rerun the original reproduction and retain a meaningful regression using the project's runner. A confirmed acceptance defect keeps delivery incomplete until fixed or explicitly accepted by the owner.

## Run

Establish the intended build, environment and disposable or authorized fixtures before acting. An open port alone does not establish identity. Drive the actual entry point and confirm material writes with a fresh authoritative read. Keep credentials and private data out of evidence.

Report outcomes consistently:

- `pass`: the named check observed the expected behavior.
- `fail`: it observed contrary behavior.
- `inconclusive`: setup or observation could not distinguish the result.
- `skipped`: applicable but not run, with a reason.
- `not applicable`: unreachable from that surface, with a reason.

Inspect selected tests, assertions, reports and relevant attempts. A green job, empty selection or zero findings does not by itself establish acceptance. Preserve the first failure; a retry pass does not erase it. Report a flaky check as flaky.

Stop only owned processes and clean up disposable state. Return the claim, actual revision/environment, action, observation and gaps. A later source change invalidates affected proof until rechecked. Use [pr](../../pr/SKILL.md) when publication is part of the task.

## Keep review evidence proportional

Keep raw logs and run artifacts ignored or in CI. Put decisive sanitized observations and useful captures in the PR or an approved artifact store, with source identities. Retain the first failure and the evidence needed to assess lasting claims; avoid duplicate captures and full run-directory commits. Follow the consuming project's retention rules.
