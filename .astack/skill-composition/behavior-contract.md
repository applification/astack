# Composable astack skills

The owner requested this architecture correction within PR 18 after finding that focused skills had been reduced to guidance behind one entry. Later steering names Matt Pocock engineering, pstack and HumanLayer as structural examples while preserving Applification's existing stack opinions.

## Outcome

Keep astack as the coordinating entry and its seven routes. Expose recognizable delivery, capability and platform workflows as independently callable skills with precise triggers, direct instructions, concrete outputs and useful examples. References support their owning workflow. Composition preserves task identity, intent, scope, acceptance, authority, revision/environment and completed results, with one writer per worktree.

## Acceptance and trial rubric

Declared before installed-candidate delivery trials. Each case reports pass/fail/inconclusive with revision, environment and source evidence; no numeric aggregate substitutes for a missing observation.

| ID | Observable case |
| --- | --- |
| C1 | The relocated package has 16 distinct matching skill identities, and linked instructions remain inside the package and resolve. Actual installed candidate bytes match the source; the execution host advertises the candidate skills and reports no candidate loading errors. |
| C2 | A direct show-me request produces a concise source-grounded view of the supplied topic outside PR preparation, without unrequested implementation or publication. |
| C3 | A direct domain-modeling request records an agreed term at the existing home, distinguishes code/definition ambiguity and returns unresolved choices instead of silently changing behavior. |
| C4 | Direct verification runs the specified meaningful checks and returns partial/failure evidence honestly, without repair or implicit PR publication. |
| C5 | Direct PR preparation reviews a supplied diff and creates the authorized local description with a useful explanation and actual proof/gaps, without an external PR or merge when excluded by the trial request. |
| C6 | An astack delivery request selects the owning implementation skill and composes relevant capabilities while preserving the user's limits and returning the consolidated observed outcome. A lightweight case does not require every skill or delegation. |
| C7 | The existing setup, control, web, MCP, ChatGPT and cloud procedures survive relocation. Direct change skills select applicable platform guidance before edits; bounded contributions return to the caller when it owns integration. |

## Execution limits

Use fresh disposable local Git fixtures and the exact candidate installed in a uniquely named trial marketplace. No publishing, push, merge, release, real provider calls, external messages, unrelated project access or recursive delegation. One writer owns each fixture. Use the configured Codex model, record observed usage, and bound each delivery to five minutes and 30 tool actions. Stop on candidate loading errors; no retry can relabel an earlier failed trial as passed. Keep raw events and logs ignored under `.proof/skill-composition/`; retain concise observations and selected outputs only.

Pen and Storybook are unnecessary for the plugin instruction changes themselves. The website documents the new callable catalog; a focused rendered inspection can establish readability, while package checks and examples establish only source consistency. These trials do not replace the foundation feature/bug delivery repeat or live WorkOS/MCP/installed-ChatGPT acceptance.
