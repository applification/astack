# Deferred foundation milestones

The foundation PR establishes a supported project, executable checks and observed delivery trials. These later capabilities remain separate work under the [iteration plan](https://chatgpt.com/space/page_b11134b1d1708191adcbfc59518d1580). Their implementation and integration behavior are unverified.

These milestones span both loops. Specialist selection, coordination, role guidance and portable assignment/result contracts belong to astack. The external chief-of-staff host owns persistent signal collection, prioritisation, deduplication, dispatch and outcome follow-up. An astack assignment can use Slack/PostHog evidence; ongoing monitoring and commissioning live in the outer host. Deferred from this PR does not mean outside the kitchen's goal or, for specialist guidance, outside astack's remit.

| Later milestone | Required result and integration evidence |
| --- | --- |
| Specialist selection and portable handoffs | Preserve the public entry and delivery routes. Define each specialist's trigger, scope, context, permitted actions, proof, report and escalation. Keep references behind the entry unless an independent skill has a concrete use. Define assignment, specialist contribution and consolidated result contracts with stable work identity, acceptance, revision, environment, findings, gaps and permitted autonomy. Support hosts with and without delegation and retain independent-review gaps. |
| Chief-of-staff host and work records | Select the actual host/version against capabilities. It owns durable state, priorities, dispatch and reconciliation. Prove restart/resume, duplicate-event and replay handling, stable work identity, bounded concurrency/retries and completion callbacks before autonomous dispatch. Replayed inputs must not create a second task, PR or message. Keep one writer per worktree and explicit ownership of shared-contract changes. |
| External pilot | Start with one owner-selected Slack signal source and authorized commissioning path, retaining source links and observed facts. Reports are candidates until reproduced. Verify triage, deduplication, bounded assignment, reviewed result and outcome follow-up against the real host. Add PostHog signals and scheduled code gardening later, after this path is demonstrated. |
| Release and outcome observation | Carry the owner's existing communication, merge and deployment authority through the handoff. Prove permitted actions, recovery arrangements and deployed/exposed revision identity, then observe the product outcome under the same work ID. A PR or merge alone does not resolve an external signal. Wider autonomy requires repeated evidence for its defined work class. |
| Periodic test-quality review | Inspect implementation-mirroring tests and duplicate coverage when reviewing recurring delivery findings and tooling changes. Link each proposed removal or consolidation to the behavior or failure it protects and the surviving check. Preserve meaningful acceptance and regression checks; confirm intended behavior remains covered before removing a test. Schedule recurring review only when the owner requests it. |
| ADR adoption beyond this reference | Extend the repository register with templates and document checks when that adoption work is selected. Inspect any existing StoryLoop decisions, identities, revisions and lifecycle history before a migration; preserve context and reciprocal supersession links. Current foundation ADRs record the accepted profile choices. |

Live WorkOS login, refresh and subject continuity, exact-resource MCP OAuth, and installed-host tool/UI proof remain the immediate external verification gaps recorded in [foundation evidence](evidence.md). The dedicated sandbox is configured; completing those observations requires the actual public MCP resource and authorized live identities.
