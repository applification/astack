# astack routing and proof examples

Use these as realistic checks when editing the skill. Judge the chosen route and actual behavior, not whether the final wording matches this file. Run tasks in a disposable project or review a recorded trial before changing a broad instruction.

Invoke each task through `$applification:astack <request>`. The user chooses only this entry point; astack chooses the route. A bare `$applification:astack` should ask for the task rather than inventing one.

| Request | Expected decision |
| --- | --- |
| "Correct a typo in the web account button label" | Small web feature; inspect whether the label affects an agreed Pencil frame or a Storybook state, decide on each tool separately, and record why. A running-app check may suffice if neither artifact helps. Open a PR; no MCP or iOS proof unless the shared component reaches them. |
| "Change the one-line label that distinguishes the destructive action in a shared confirmation component" | Inspect the agreed visual direction and component states. Even with one code line, update the Pencil frame if the visual decision changes and Storybook if the shared confirmation state needs a regression example. Check the real confirmation path and record both tool decisions in the PR. |
| "Users lose an edit after saving and reopening" | Bug route; reproduce the lost edit before changing code, then rerun that exact path and a fresh read; open a PR with the before/after evidence. |
| "Move the document parser behind a smaller interface without changing outputs" | Refactor route; pin existing outputs and compare them after the move, then open a PR with the equivalence evidence. |
| "Why was the tenant check placed in the backend?" | Read-only investigation; inspect code and decision history, no PR or app run unless needed to answer. |
| "Add a new mobile planning flow; I'm unsure how it should feel" | Short behavior contract and affected-surface proof. Resolve product choices before production wiring; open a PR. If the feature also has a web UI, decide separately whether Pencil and Storybook would help that surface. |
| "In an empty repo, build a client-side reading list" | Create Bun workspaces and Turborepo with `apps/web` (Next.js App Router + TypeScript) and `packages/ui` (shadcn/ui + Tailwind); start web development through Portless, decide whether the first UI needs Pencil and Storybook, establish shadcn lint, prove the running app through its actual URL, and open a PR. |
| "In an empty repo, build a web dashboard with server-rendered private data" | Create Bun workspaces and Turborepo with a Next.js App Router app, shared UI package, and Convex backend package; start through Portless, decide whether the initial dashboard needs Pencil and Storybook, prove identity and data behavior in the running app, and open a PR. |
| "In an empty repo, build a reading list that survives reload" | Create Bun workspaces and Turborepo with Next.js in `apps/web`, `packages/ui`, and `packages/backend/convex`; use Portless for local web startup and local Convex with `bunx`, decide whether Pencil or Storybook clarifies UI states, prove a saved item with a fresh database read, and open a PR. |
| "Start a new Next.js and shadcn app with Convex" | Consult `@Convex` new-app guidance and runbook first; use `$convex:quickstart` if its scaffold fits, then reconcile output with Bun workspaces and the backend package. Use `$convex:convex-expert` for backend edits and `$convex:convex-reviewer` before the PR is ready. |
| "Add Convex to our existing Vite app" | Use `@Convex` existing-project setup guidance with the actual framework and package manager; do not run `$convex:quickstart` or mistake `$convex:add` for the initializer. Review backend edits with the expert skill and the PR with the reviewer skill. |
| "Add search to the existing Convex + Next.js app" | Use `$convex:add` to consult the live capability catalog, then `$convex:convex-expert` for changes under `convex/`; verify the running path and require `$convex:convex-reviewer` before the PR is ready. |
| "Review a PR that changes convex/schema.ts and a mutation" | Run `$convex:convex-reviewer` against the diff. Resolve confirmed findings and rerun affected checks before marking ready; keep the PR in draft if the specialist review cannot run. |
| "In an empty repo, build a web flow with a timed confirmation" | Use the Pencil/Storybook design sprint to develop one behavior contract: link chosen frames and stories to material acceptance cases, then use agent-browser to prove the timed interaction in the running app; capture a short recording if timing matters, and open a PR with the contract and evidence. |
| "Build a four-state presence preview like Loami" | Track `.astack/project.md` and a `.astack/presence/` folder containing the behavior contract, Pencil file and supporting assets, and retained evidence. Tie `.pen` frames and Storybook story IDs to acceptance cases, then drive the running app to prove transitions. Ensure `.astack/` is not Git ignored; do not create root `design/` or `docs/` feature folders. |
| "Add an MCP-only tool" | Behavior contract and implementation, then direct client checks of schema, success, errors and permissions; connect to the running endpoint if transport or deployment is affected. Add an agent check when the model must discover or choose the new tool. Open a PR; no Pencil, Storybook, or shadcn lint without a web UI. |
| "In an empty repo, build an authenticated remote MCP tool" | Start Bun/Turborepo with `apps/mcp`; use an HTTP MCP adapter and verify token validation, resource discovery, direct calls and the running HTTP endpoint. Add shared packages only for real consumers. No web UI package, Pencil, Storybook, or Convex unless the feature needs them. |
| "In an empty repo, build a local stdio MCP tool" | Start with `apps/mcp` and the MCP SDK's stdio transport. Do not add Hono, HTTP auth or an HTTP adapter without a requirement for them; prove a spawned client can initialize and call the tool. |
| "Adopt astack in an existing pnpm app" | Inspect scripts and CI; keep pnpm and the current layout, document working proof commands, and add project-owned app control only where repeatable driving is useful. Do not migrate the package manager as part of adoption; open a PR. |
| "Set up astack to verify our existing web app" | Inspect its current drivers, framework, package manager, and scripts; create or adopt a project-owned executable `astack-<app>` CLI in `.codex/skills/` and feature map in `.astack/feature-map/<app>/`, prove its direct invocation and one real user path through the CLI, and open a PR. The command must drive the app, not merely wrap lint and tests; keep the working stack. |
| "The app control script has a Bun shebang but only `bun run` works" | Check and commit executable mode, document and prove direct checkout-local invocation and `--help`, and keep any package script as a convenience alias. Do not set up the user's `PATH`. |
| "Create a new Bun app control CLI with doctor and browser commands" | Use a Bun shebang, Git executable mode, and Commander for subcommands and help. Prove the direct checkout-local command and a real user path; a root package script is optional and global `PATH` setup is left to the user. |
| "The app already has a working control CLI and feature guide" | Reuse the working commands, align their skill and map with astack's proof requirements, and avoid a duplicate driver. |
| "A different checkout already owns the usual dev port" | For a new Next.js app, Portless assigns a separate upstream port and a worktree-specific URL. `astack-<app> doctor` reports that URL and verifies its route and process belong to this checkout. It must not stop the other checkout's process. |
| "A headless agent starts a new Next.js app before Portless trust is configured" | Report the failed proxy or certificate preflight and exact interactive setup needed. Do not drive another checkout's route or quietly switch to a fixed port. |
| "Next DevTools reports a route error while the browser still renders a page" | Confirm the DevTools connection points at this checkout, inspect the runtime error, then use the control CLI and browser to establish the affected user-path outcome. Do not treat a framework diagnostic as browser proof. |
| "Review a new shared React component with many mode flags" | If installed, use Vercel Labs `composition-patterns` for the component API and `web-design-guidelines` for the relevant interaction; check the rendered Storybook state and user path before claiming it works. |
| "The saved-items menu moved and the control command can no longer reach it" | Repair the app-specific command and affected map entry in the same PR; re-drive the path and distinguish a stale handle from a product regression. |
| "Make a pure parsing library controllable like a web app" | Keep its executable library checks and examples; do not invent a browser, app session, or user feature map for a surface that does not exist. |
| "Cut report generation from four seconds to two" | Performance route; measure the same user path before and after, report limitations, and open a PR for the change. |
| "Review PR #42 and fix the confirmed regression" | Review against intent and proof, make the authorized fix, and update PR #42 rather than opening another PR. |
| "Finish the PR after browser proof captured a screenshot" | Attach the screenshot to the PR or link its committed copy. If proof captured no media, explain why it would not help review; do not demand a video by default. |
| "The backend now returns another field used by MCP" | Select focused backend and MCP checks even if no MCP source file changed. |
| "Rewrite MCP tool descriptions so an agent picks the right action" | Check the listed tool contract, then run a small model-driven tool-choice evaluation using natural prompts against the current descriptions. Direct calls alone cannot establish agent choice; inspect actual calls and final results before claiming success. |
| "Test our MCP client while the external tool server is unavailable" | A mock MCP server can provide deterministic client fixtures. Treat this as consumer proof, not proof of the external server. |
| "Update a web-only illustration" | Select visual proof on web; explain why server and unrelated client checks do not apply. |
| "Implement the proposed design despite an unresolved delete-confirmation choice" | Ask for the product decision before coding that branch; continue independent work. |

| "Add our app to the ChatGPT sidebar and conversation panel" | Feature route with ChatGPT plugin guidance. Verify SDK peers, empty launch inputs, shared MCP App UI and target host capabilities; prove actual installed entrypoints separately from Storybook and protocol checks. |
| "Expose our shared React components inside ChatGPT" | Use the MCP App UI path, keep host APIs in an adapter, bundle components as a versioned HTML resource, choose Storybook states and verify standard bridge lifecycle. Do not embed Storybook or require a framework migration. |
| "Let users open a specific record through a plugin deep link" | Validate the global-entrypoint route and encoded identity/path, handle initial and changed host context, recheck record access and prove navigation in the supported host. Android deep-link coverage remains unsupported at launch. |
| "Let users mention records in the ChatGPT composer" | Use authorized bounded mention search with an empty-query case and app visibility. Prove selection in desktop; do not claim Work web or mobile composer mentions. |
| "Ask users to choose an image in a registered plugin form" | Use MCP 2026-07-28 MRTR and validate accept, decline and cancel without duplicate effects. Do not copy the legacy OpenAI elicitInput helper into registered-server guidance. |
| "Monitor document updates and act in ChatGPT" | Use MCP Events with user-authorized subscriptions, durable filters, verified signed callbacks, expiry and idempotent unsubscribe. Prove lifecycle locally and the intended response in ChatGPT; webhook 2xx is receipt only. |
| "Make our private local MCP server available to Work web" | Use a reachable HTTPS development endpoint or Secure MCP Tunnel with actual workspace association and runtime credentials. Installing a local folder does not expose localhost to Work web. |
| "Package this plugin using the latest manifest format" | Use root plugin.json and mcp.json with portable schemas and explicit transport types; put OpenAI metadata under extensions.com.openai, validate relocated assets/scripts and avoid fallback manifests. |
| "MCP Jam passes, can we claim our sidebar integration works?" | Investigation route; distinguish protocol and emulated-host evidence from actual installed ChatGPT proof. Run the real entrypoint or report that claim unverified. |
| "Use the OpenAI extensions helper with the split v2 SDK" | Inspect the chosen published peers and compatibility ledger. Do not suppress peer errors or cast incompatible servers; prove a supported profile or an explicit adapter before claiming combined support. |

After a trial, record whether astack chose the right route, found an important missing decision, selected checks proportionately, and reported proof honestly. Fix an observed failure narrowly rather than adding more universal gates.
