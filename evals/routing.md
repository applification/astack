# astack routing and proof examples

Use these as realistic checks when editing the skill. Judge the chosen route and actual behavior, not whether the final wording matches this file. Run tasks in a disposable project or review a recorded trial before changing a broad instruction.

Invoke each task through `$applification:astack <request>`. The user chooses only this entry point; astack chooses the route. A bare `$applification:astack` should ask for the task rather than inventing one.

| Request | Expected decision |
| --- | --- |
| "Correct a typo in the web account button label" | Small web feature; inspect whether the label affects an agreed Pencil frame or a Storybook state, decide on each tool separately, and record why. A running-app check may suffice if neither artifact helps. Open a PR; no MCP or iOS proof unless the shared component reaches them. |
| "Change the one-line label that distinguishes the destructive action in a shared confirmation component" | Inspect the agreed visual direction and component states. Even with one code line, update the Pencil frame if the visual decision changes and Storybook if the shared confirmation state needs a regression example. Check the real confirmation path and record both tool decisions in the PR. |
| "Users lose an edit after saving and reopening" | Bug route; reproduce the lost edit before changing code, then rerun that exact path and a fresh read; open a PR with the before/after evidence. |
| "Move the document parser behind a smaller interface without changing outputs" | Refactor route; pin existing outputs and compare them after the move, then open a PR with the equivalence evidence. |
| "Why was the tenant check placed in the backend?" | Read-only investigation; inspect code and decision history, no PR or app run unless needed to answer. |
| "Add a new mobile planning flow; I'm unsure how it should feel" | Short behavior contract and affected-surface proof. Resolve product choices before production wiring; open a PR. If the feature also has a web UI, decide separately whether Pencil and Storybook would help that surface. |
| "In an empty repo, build a client-side reading list" | Create Bun workspaces and Turborepo with `apps/web` (React + TypeScript + Vite) and `packages/ui` (shadcn/ui + Tailwind); use Portless, decide whether the first UI needs Pencil and Storybook, establish shadcn lint, prove the running app through its actual URL, and open a PR. Add persistence or MCP only when the behavior needs them. |
| "In an empty repo, build a web dashboard with server-rendered private data" | Choose Next.js App Router for the stated server-rendering requirement, with Bun workspaces, Turborepo, shared UI and Convex; follow its documented WorkOS integration, use Portless, decide whether Pencil and Storybook help, prove identity and data behavior in the running app, and open a PR. |
| "In an empty repo, build a reading list that survives reload" | Create Bun workspaces and Turborepo with React + TypeScript + Vite in `apps/web`, `packages/ui`, and `packages/backend/convex`; use Portless and a named Convex development deployment, decide whether Pencil or Storybook clarifies states, prove a saved item with a fresh database read, and open a PR. |
| "Start a persistent work-item app on web and MCP with no chosen stack" | Use the foundation reference: Bun/Turbo, React + TypeScript + Vite, portable UI, pure domain rules, Convex data and HTTP MCP serving, and WorkOS web sessions plus Connect OAuth. Generate a separate project, consume its selected Pen frames and exported design specification before UI changes, run design:verify with visual comparison and the scoped readiness commands, and keep live OAuth, installed-host and fresh-agent trial gaps explicit. |
| "Build a new Convex app before deciding whether it is worth hosting" | Start with persistent local Convex development, guard against cloud targets and keys, and preserve data across restarts. Configure local WorkOS login when needed; leave public integration proof explicit. The user decides when to move to cloud. |
| "Move this local app to cloud" | Use the cloud transition workflow: resolve the actual project, deployment and frontend host, ask empty versus selected-data transfer, preserve local configuration and backups, update frontend/WorkOS/MCP settings, deploy to the explicit target, verify actual hosted behavior and retain recovery. |
| "Build a public documentation site that needs server-rendered content" | Choose Next.js for the stated content and rendering requirement, keep its documented framework integrations, and add only the packages with real consumers. The Vite interactive UI default does not override the requested output medium. |
| "Use TanStack Form for a Vite form backed by Convex" | Use its documented Zod validation with accessible native controls and pending/error handling. Keep form input state local, server validation and authorization in Convex, and query subscriptions in Convex; TanStack Form does not require a second Query cache. |
| "Add a form to our existing Next.js app" | Preserve Next.js and use the platform's documented form path where applicable, including validation, pending/error handling and authorization inside the server operation. Do not impose the Vite reference's form library or migrate the framework. |
| "Import Convex and the MCP host bridge into the shared work-item component" | Keep the shared component portable through data and action props. Put the Convex adapter in web and the host bridge in MCP UI; retain a boundary check that rejects the forbidden shared-package imports. |
| "A pure title-normalization rule lives in a .tsx file" | Select a focused logic check for the rule and real-browser checks only for affected rendered interactions. Choose by behavior and consumers; the extension neither requires nor forbids the test. |
| "Web and MCP can identify me, so remove the backend ownership check" | Keep ownership and write preconditions at the backend operation. WorkOS web sessions and Connect resource tokens have distinct validation contracts; successful authentication on either surface cannot authorize another user's work item. |
| "Run the foundation checks after a shared backend change" | Use `check:quick` for fast scoped feedback, then `check:affected` with the intended Git base and review indirect web/MCP consumers. Run `check:ci` at delivery and selected real-product checks; report the actual selection and evidence. |
| "Foundation CI is green but no live WorkOS account or MCP host was used" | Record deterministic checks as their own result. Run disposable readiness for local behavior, and leave live OAuth and installed-host claims skipped or inconclusive with prerequisites; neither local signed fixtures nor CI establish them. |
| "Start a new Next.js and shadcn app with Convex" | Consult `@Convex` new-app guidance and runbook first; use `$convex:quickstart` if its scaffold fits, then reconcile output with Bun workspaces and the backend package. Use `$convex:convex-expert` for backend edits and `$convex:convex-reviewer` before the PR is ready. |
| "Add Convex to our existing Vite app" | Use `@Convex` existing-project setup guidance with the actual framework and package manager; do not run `$convex:quickstart` or mistake `$convex:add` for the initializer. Review backend edits with the expert skill and the PR with the reviewer skill. |
| "Add search to the existing Convex + Next.js app" | Use `$convex:add` to consult the live capability catalog, then `$convex:convex-expert` for changes under `convex/`; verify the running path and require `$convex:convex-reviewer` before the PR is ready. |
| "Review a PR that changes convex/schema.ts and a mutation" | Run `$convex:convex-reviewer` against the diff. Resolve confirmed findings and rerun affected checks before marking ready; keep the PR in draft if the specialist review cannot run. |
| "In an empty repo, build a web flow with a timed confirmation" | Use the Pencil/Storybook design sprint to develop one behavior contract: link chosen frames and stories to material acceptance cases, then use an exact e2e check to prove the timed interaction in the running app, preserving an existing runner when present; capture a short recording if timing matters, and open a PR with the contract and evidence. |
| "Build a four-state presence preview like Loami" | Track `.astack/project.md` and a `.astack/presence/` folder containing the behavior contract, Pencil file and supporting assets, and retained evidence. Tie `.pen` frames and Storybook story IDs to acceptance cases, then drive the running app to prove transitions. Ensure `.astack/` is not Git ignored; do not create root `design/` or `docs/` feature folders. |
| "Add an MCP-only tool" | Behavior contract and implementation, then direct client checks of schema, success, errors and permissions; connect to the running endpoint if transport or deployment is affected. Add an agent check when the model must discover or choose the new tool. Open a PR; no Pencil, Storybook, or shadcn lint without a web UI. |
| "In an empty repo, build an authenticated remote MCP tool" | Use WorkOS Connect for the default OAuth profile and prove resource discovery, token audience/issuer validation, direct calls and the running endpoint. Serve it in Convex when persistent domain behavior needs the foundation; otherwise use an appropriate `apps/mcp` runtime. Add only packages with real consumers, and no UI design tools without UI. |
| "In an empty repo, build a local stdio MCP tool" | Start with `apps/mcp` and the MCP SDK's stdio transport. Do not add Hono, HTTP auth or an HTTP adapter without a requirement for them; prove a spawned client can initialize and call the tool. |
| "Adopt astack in an existing pnpm app" | Inspect scripts and CI; keep pnpm and the current layout, document working proof commands, and add project-owned app control only where repeatable driving is useful. Do not migrate the package manager as part of adoption; open a PR. |
| "Set up astack to verify our existing web app" | Inspect its current drivers, framework, package manager, and scripts; create or adopt a project-owned executable `astack-<app>` CLI in `.codex/skills/` and feature map in `.astack/feature-map/<app>/`, prove its direct invocation and one real user path through the CLI, and open a PR. The command must drive the app, not merely wrap lint and tests; keep the working stack. |
| "The app control script has a Bun shebang but only `bun run` works" | Check and commit executable mode, document and prove direct checkout-local invocation and `--help`, and keep any package script as a convenience alias. Do not set up the user's `PATH`. |
| "Create a new Bun app control CLI with doctor and browser commands" | Use a Bun shebang, Git executable mode, and Commander for subcommands and help. Prove the direct checkout-local command and a real user path; a root package script is optional and global `PATH` setup is left to the user. |
| "The app already has a working control CLI and feature guide" | Reuse the working commands, align their skill and map with astack's proof requirements, and avoid a duplicate driver. |
| "A different checkout already owns the usual dev port" | For a new Vite or Next.js app, Portless assigns a separate upstream port and worktree-specific URL. `astack-<app> doctor` reports that URL and verifies its route and process belong to this checkout. It must not stop the other checkout's process. |
| "A headless agent starts a new Next.js app before Portless trust is configured" | Report the failed proxy or certificate preflight and exact interactive setup needed. Do not drive another checkout's route or quietly switch to a fixed port. |
| "Next DevTools reports a route error while the browser still renders a page" | Confirm the DevTools connection points at this checkout, inspect the runtime error, then use the control CLI and browser to establish the affected user-path outcome. Do not treat a framework diagnostic as browser proof. |
| "Review a new shared React component with many mode flags" | If installed, use Vercel Labs `composition-patterns` for the component API and `web-design-guidelines` for the relevant interaction; check the rendered Storybook state and user path before claiming it works. |
| "The saved-items menu moved and the control command can no longer reach it" | Repair the app-specific command and affected map entry in the same PR; re-drive the path and distinguish a stale handle from a product regression. |
| "Make a pure parsing library controllable like a web app" | Keep its executable library checks and examples; do not invent a browser, app session, or user feature map for a surface that does not exist. |
| "Cut report generation from four seconds to two" | Performance route; measure the same user path before and after, report limitations, and open a PR for the change. |
| "Review PR #42 and fix the confirmed regression" | Review against intent and proof, make the authorized fix, and update PR #42 rather than opening another PR. |
| "Finish the PR after browser proof captured a screenshot" | Attach the screenshot to the PR or link its committed copy. If proof captured no media, explain why it would not help review; do not demand a video by default. |
| "The backend now returns another field used by MCP" | Select focused backend and MCP checks even if no MCP source file changed. |
| "Rewrite MCP tool descriptions so an agent picks the right action" | Check the listed tool contract, then run a small model-driven tool-choice evaluation using natural prompts against the current descriptions. Direct calls alone cannot establish agent choice; inspect actual calls and final results before claiming success. |
| "Test our MCP client while the external tool server is unavailable" | A mock MCP server can provide deterministic client fixtures. Treat this as consumer proof, not proof of the external server. |
| "Update a web-only illustration" | Select visual proof on web; explain why server and unrelated client checks do not apply. |
| "Implement the proposed design despite an unresolved delete-confirmation choice" | Ask for the product decision before coding that branch; continue independent work. |

| "Add OpenAI plugin extensions for a ChatGPT sidebar and conversation panel" | Feature route → ChatGPT plugin engineering → OpenAI extensions and MCP App UI guidance. Check SDK compatibility, define entrypoints with empty launch inputs, and share the UI through a versioned MCP App resource. Choose useful component states in Storybook, then prove the sidebar and conversation panel in the supported ChatGPT host. |
| "Build an MCP App using our shared React UI components" | Feature route → MCP server and web feature paths → ChatGPT plugin engineering and MCP App UI guidance. Keep presentation components in the UI package and host APIs in an adapter. Bundle a versioned HTML resource, register the UI tool/resource metadata, choose Storybook states, and prove bridge initialization, tool input/results and teardown in the target host. |
| "Let users open a specific record through a plugin deep link" | Validate the global-entrypoint route and encoded identity/path, handle initial and changed host context, recheck record access and prove navigation in the supported host. Android deep-link coverage remains unsupported at launch. |
| "Let users mention records in the ChatGPT composer" | Use authorized bounded mention search with an empty-query case and app visibility. Prove selection in desktop; do not claim Work web or mobile composer mentions. |
| "Ask users to choose an image in a registered plugin form" | Use MCP 2026-07-28 MRTR and validate accept, decline and cancel without duplicate effects. Do not copy the legacy OpenAI elicitInput helper into registered-server guidance. |
| "Monitor document updates and act in ChatGPT" | Use MCP Events with user-authorized subscriptions, durable filters, verified signed callbacks, expiry and idempotent unsubscribe. Prove lifecycle locally and the intended response in ChatGPT; webhook 2xx is receipt only. |
| "Make our private local MCP server available to Work web" | Use a reachable HTTPS development endpoint or Secure MCP Tunnel with actual workspace association and runtime credentials. Installing a local folder does not expose localhost to Work web. |
| "Package this plugin using the latest manifest format" | Use root plugin.json and mcp.json with portable schemas and explicit transport types; put OpenAI metadata under extensions.com.openai, validate relocated assets/scripts and avoid fallback manifests. |
| "MCP Jam passes, can we claim our sidebar integration works?" | Investigation route; distinguish protocol and emulated-host evidence from actual installed ChatGPT proof. Run the real entrypoint or report that claim unverified. |
| "Use the OpenAI extensions helper with the split v2 SDK" | Inspect the chosen published peers and compatibility ledger. Do not suppress peer errors or cast incompatible servers; prove a supported profile or an explicit adapter before claiming combined support. |

| "Start a new web app with repeatable verification" | Use e2e for running-app regressions and live MCP inspection; pin compatible dependencies and install version-matched project guidance. Prove the intended instance and one exact path; keep app control, backend and host proof at their own boundaries. |
| "Adopt astack in an app with working Playwright regressions" | Preserve Playwright and the package manager. Map acceptance to existing checks, retain evidence and use the candidate confirmation loop; do not migrate the runner without a request. |
| "Exploration CI is green but the charter timed out with no findings" | Read report steps, assessment and termination. Record the charter as inconclusive despite exit zero; no acceptance case passes without an independent check. Keep required regressions separate. |
| "An explorer says saving lost data, but its repro failed during login" | Leave the finding a candidate. Login/setup failure is inconclusive; repair fixtures and reproduce the relevant body assertion, including an independent persistence read, before confirming. |
| "An explorer flags intended disabled controls as a bug" | Check the behavior contract and source artifacts, then reject with evidence and a reason. Preserve the original claim and do not change intended behavior to satisfy the explorer. |
| "The known failing probe is excluded, so can the PR be ready" | Excluding a repro from the passing suite does not waive a confirmed acceptance defect. Fix it and retain the passing regression, or obtain explicit owner acceptance of the limitation. |
| "The regression passed only on retry" | Record the latest pass and flaky status, preserve the first failure, and investigate or obtain explicit acceptance before claiming the affected case verified. |
| "The test server belongs to another checkout" | Refuse to drive it; classify the identity/setup failure as inconclusive. Start an isolated owned instance or resolve the CLI-owned URL and build/run identity. Never stop another checkout's process. |
| "The rerun failed before writing a fresh report" | Keep the original report and artifacts unchanged. Separate the selection seed from fresh evidence and report the rerun inconclusive; do not relabel the prior report as a new observation. |
| "A backend change alters the browser save flow" | Select the affected browser regression and a focused persistence/state charter even without frontend changes. Confirm writes through a fresh independent read; backend checks alone may miss the user-path regression. |
| "Update only the verification docs" | Run documentation, package and site consistency checks. Skip app exploration because no product behavior changed; a new executable reference still needs its own real checks. |
| "The e2e MCP config file exists, so claim Codex inspection works" | Prove stdio initialize/open/observe/locate/close and actual host configuration loading separately. A launcher test does not establish that a restarted Codex host loaded it. |
| "A cached agent action passed, so claim the new model chooses correctly" | Record replay separately and run live without cache for model-choice claims. Cached actions can support their exact observed outcome, not fresh model behavior. |
| "The CI artifact link has expired" | Name the evidence gap and rerun if necessary. Retain sanitized evidence supporting lasting claims under the feature folder or a durable approved store, beyond short CI expiry. |

## PR explanation selection

These are interpretation cases; posted explanation inspection and delivery proof are separate observations.

| Request | Expected decision |
| --- | --- |
| "Prepare a PR for a backend permission change with no UI change" | PR route; show the actual actor and authorization boundary with a compact flow or sequence diagram when it helps review, link the changed source and cases, and report allowed/denied observations separately. No invented UI screenshot or diagram-as-proof claim. |
| "Open a PR for a one-word label correction" | Keep the PR concise with the intended label and relevant observed check. Skip an additional explanation diagram that would repeat the sentence; retain useful captured media under the existing policy. |
| "Prepare a PR after moving state and adapters between packages" | PR route; use a shallow before/after responsibility or component tree grounded in actual paths and state owners. Preserve enough context to assess the boundary, and link equivalence/integration evidence separately. |
| "Explain a proposed UI layout in a PR using an HTML illustration" | Use a focused illustration only when simpler views are inadequate; render and inspect it, label it as proposed, and include an accessible capture/artifact and text equivalent in the PR. A local path is not a shareable PR artifact; illustrative rendering does not prove product behavior. |
| "The PR diagram describes the earlier diff after a later implementation change" | Refresh the view and source links from the current diff, inspect the posted explanation, and rerun only proof the later change could affect. Keep the explanation current without relabeling old observations as new proof. |

## Domain language selection

These interpretation cases cover terminology, scope and document ownership; they do not establish observed agent delivery.

| Request | Expected decision |
| --- | --- |
| "The glossary defines cancellation for one reservation but the code cancels the whole visit" | Surface the glossary/code contradiction with source evidence and a distinguishing case. Investigate whether it is a defect or a product choice; resolve material meaning with the owner before dependent edits. Do not silently redefine cancellation to match code. |
| "We agreed our first domain term but this project has no glossary" | Reuse any established term location; otherwise create root GLOSSARY.md now with the agreed concise definition and useful relationships or confusing alternatives. Keep acceptance and implementation detail elsewhere; do not create an empty context map or a routine ADR. |
| "Change the billing Account concept in a repo with a GLOSSARY-MAP.md" | Follow the map to the billing glossary and relevant decisions, inspect affected code and cases, and preserve distinct meanings in other contexts. Resolve material ambiguity and reconcile changed definitions and acceptance within scope; do not flatten context glossaries. |
| "Fix punctuation in a label that already uses the agreed domain term" | Keep the fix lightweight and use settled terminology. Run proportionate checks and prepare a concise PR; no new glossary, ADR or separate modeling session is needed. |
| "While fixing this one screen, we agreed Reservation is the canonical term" | Record the agreed meaning promptly, then keep code changes within the authorized scope. Surface the wider rename and affected public or persisted consumers as a separate scope decision; terminology agreement alone does not authorize a repository-wide migration. |
| "Put our cache expiry and retry implementation in GLOSSARY.md" | Keep the glossary focused on agreed domain meanings. Put operational detail in relevant project documentation; use the existing decision register only for a consequential tradeoff whose rationale merits retention. Link acceptance cases separately. |

After a trial, record whether astack chose the right route, found an important missing decision, selected checks proportionately, and reported proof honestly. Fix an observed failure narrowly rather than adding more universal gates.
