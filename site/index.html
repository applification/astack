A reusable engineering stack for coding agents. Skills say how to do the work, lint rules push back when it breaks a rule, and loops run the skills on a schedule or a mention. Install the Applification plugin in Codex or Claude Code, then give astack an engineering request.

LINT RULES

Rules that answer back
before review does.

A skill tells an agent what to do. A lint rule tells it when it didn’t. Each message says what to do instead, so the agent can fix the cause without rereading the skill.

Add it to a project

bun add -d github:applification/astack eslint typescript

// eslint.config.mjs
import astack from 'astack/eslint';

export default astack({ scope: '@acme' });

// tsconfig.json
{ "extends": "astack/tsconfig" }

scope is your workspace package scope. The config expects apps in apps/* and shared code in packages/ui, packages/domain and packages/backend.

What it enforces

  • Strict types. No floating promises, no unsafe any access, exhaustive switches.
  • React and accessibility. Hook rules and accessible names in .tsx files.
  • Portable UI. UI and domain packages cannot import the backend, Node builtins or network clients, or call fetch directly.
  • Pure domain. No window or document in the domain package.

When a rule can be checked mechanically it belongs here, and the skill gets shorter.

LOOPS

The same skills,
without being asked.

A loop is one prompt file that names a trigger and the skills it composes. astack ships no scheduler: run a loop from cron, a CI schedule or your host’s scheduled tasks.

WEEKLYlint-debt

Fixes one lint rule’s findings and opens a pull request.

HOURLY OR ON PRpr-review

Reviews open pull requests and reports what the checks showed.

DAILYbug-fix

Reproduces and fixes the oldest unassigned bug.

ON A MENTIONmention

Answers the question or makes the requested change.

Run one. From a project with the plugin installed, pass the file on stdin: claude -p < loops/lint-debt.md.

Bounded. Each run does one slice of work, continues an open pull request instead of opening a second, and never merges.

Mentions. Have the trigger append the comment and its thread to the mention prompt.

04 / WEB UI

A design sprint
with one contract.

For a substantial behavior change, the tracked contract names the outcome and acceptance cases. Pencil and Storybook are selected independently when they help answer a design or component question.

From choice to proof

  1. Start the contract.Record the actor, problem, outcome, material states, open choices and observable cases.
  2. Design consequential states.If Pencil helps, keep the .pen file and its assets in the feature folder.
  3. Exercise components.If Storybook helps, put stories beside components and run the project's UI checks.
  4. Compare and record.When both tools are selected, compare the story with the chosen frame. Link frame and story IDs to the cases they support.
  5. Prove in the product.Implement the real data path, then record running-product observations and retained evidence against the same cases.

A small change can keep its outcome and tool decisions in the PR. An unavailable selected check remains an explicit gap.

What a contract looks like

Illustrative excerpt. Plain acceptance sentences work as well as Given/When/Then.

## Outcome
A member can see when another member is idle.

## Acceptance
A1. After two minutes of inactivity, the
    member's avatar shows the Idle state.
    Design: presence.pen → "Idle"
    Story:  presence-avatar--idle
    Proof:  pass · local · 3f2a91c
            evidence/a1.png

## Open decision
Should "away" hide the last-seen time?

A frame supports a visual decision. A story supports component states. Neither establishes timing, real data effects or persistence in the running app.

When domain concepts change, clarify terms against the existing glossary, code and concrete cases. Record agreed definitions in the glossary, acceptance in the contract and consequential rationale in the decision register. Follow existing context maps; create files only when needed. 07 / FINISHING THE WORK

Say what passed.
Show what was checked.

Proof names a revision, environment, action and observed result. A later code change calls for a new check when it could affect that result.

CHOOSE THE CHECK

Match evidence to the claim

  • Component story for rendering or interaction states.
  • Focused test for domain or protocol behavior.
  • Running product for data, identity, timing or integration.
  • MCP layers for tool contract, transport and agent choice where applicable.
REPORT THE RESULT

Keep gaps visible

Record pass, fail, inconclusive, skipped or not applicable with a reason. A green exploration job can still be inconclusive when steps fail or budgets expire. Confirm candidates with exact assertions and preserve the first failure when a retry passes.

When proof captures a screenshot or recording, attach it to the PR or link retained media. If no media helps review, say why.

OPEN THE PR

Connect outcome and evidence

The PR states why the work happened, what changed, the affected users or systems, the contract when there is one, and observed results with gaps.

Use the show-me skill ↗ when it clarifies the change. An illustration explains the design; actual observations establish proof. Blocked design, proof or required specialist review stays visible in a draft PR. Investigation alone ends with an answer.
