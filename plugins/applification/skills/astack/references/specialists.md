# Specialist contributions

Specialists contribute within the existing delivery route; they are not additional routes. The lead owns intent, acceptance, integration, findings resolution and the consolidated [result](handoffs.md). Feature delivery and bug diagnosis are normally lead responsibilities under [work routes](routes.md); split a contribution only when a bounded domain investigation or implementation benefits the task.

## Select by behavior and risk

Inspect the intended outcome, diff or proposed boundaries, project profile, accepted ADRs and available evidence. Select contributions that can resolve a specific uncertainty, protect an affected boundary or supply a required review. Record the selected roles and purpose briefly in the assignment or PR. Reassess when investigation changes the scope.

A local label correction with no changed interaction can use the lead and a visible check. A permissions change shared by web and MCP needs backend/data and security attention plus checks on both reachable surfaces. A new interactive flow may need UI/UX, accessibility and web expertise. A slow path needs performance expertise only when a measurement or stated performance requirement makes it relevant. File count, extension and a generic role roster do not settle selection.

One person or agent can cover several roles. Read only applicable guidance. Do not spawn a specialist for each row or add an independently invocable skill merely to name a role. Use the focused astack skill that owns the assigned job: feature delivery uses [implement](../../implement/SKILL.md), bug diagnosis uses [bug-fix](../../bug-fix/SKILL.md), performance uses [performance](../../performance/SKILL.md), and delivery review uses [pr](../../pr/SKILL.md). Existing project or companion skills supply concrete platform procedures, including the required Convex review. These role briefs add contribution scope and reporting; they do not replace the callable workflow.

## Contribution brief and ownership

Use the [specialist brief](handoffs.md#specialist-brief) to give the contributor the work identity, precise question/cases, relevant source and project context, revision/environment, permissions and execution limits. Missing context must be reported rather than invented.

Name one active writer for each worktree. Read-only reviewers may inspect a pinned revision concurrently; they must report if the working tree changes underneath the review. Independent implementation uses separate worktrees and an agreed integration owner. Before editing a shared schema, API, component contract or check policy, name its owner and coordinate dependent work. A specialist cannot silently broaden scope, weaken acceptance or grant authority to another agent.

With delegation available and permitted, assign bounded work to a fresh contributor when independence or parallel investigation adds value. Require a contribution report, inspect its evidence, and integrate under the lead's ownership. Without delegation, the lead applies the same role guidance sequentially and identifies the reviewer as the lead; this is self-review. Report any required independent review as outstanding. Never describe loading a reference, another model turn in the same context, or a self-check as independent review.

## Role guidance

The common brief, authority bounds and report requirements above apply to every row. These are contributions to select, not a mandatory team.

| Feature delivery: accepted behavior crosses separable domains or needs a dedicated implementation owner. | Outcome, cases, dependencies, existing entry points and design decisions. | Trace trigger through data and effects; implement the assigned slice as its named writer; coordinate integration with the lead. | Affected cases in the actual product, including fresh reads for material writes. | Conflicting intent, dependencies or a material product choice; do independent work first. |
| Bug diagnosis: reported failure has uncertain cause, shared impact or needs focused reproduction. | Original symptom/source, fixture, environment, history and known attempts. | Reproduce; distinguish product failure from setup; change the supported cause only if assigned write authority. Separate fixtures from live provider observations. | Missing authority for a sensitive test, confirmed access failure or an unresolved policy. Keep credentials out of reports. |
| UI and UX: new/changed journey, destructive flow, confusing states or a material visual decision. | User goal, state/interaction contract, chosen design and existing component conventions. | Examine flow, content, pending/error/empty states; propose or implement assigned interactions. Use [web feature guidance](../../web-feature/SKILL.md) for Pencil/Storybook decisions. | Meaningful rendered states and the actual user journey; design comparison where selected. | Unresolved user flow or conflicting product/design intent before dependent wiring. |
| Accessibility: affected interaction, semantics, navigation, focus or an accessibility requirement. | Journey, controls, keyboard/focus expectations and project accessibility criteria. | Inspect semantics, labels, keyboard and focus; run relevant automation and manual interaction. Fix within assigned scope. | Automated findings plus keyboard/focus observations and relevant assistive technology checks; name unavailable coverage. | Inaccessible acceptance path or missing required device/assistive technology; no claim from automation alone. |
| Web and embedded host: changed browser routing, rendering, adapter, data flow or host bridge. | Client/host entry points, state owners, backend contract and supported browser/host. | Work on browser/adapter boundaries while keeping shared UI portable; use [web](../../web-feature/SKILL.md) or [plugin engineering](../../chatgpt-plugin/SKILL.md) as applicable. | Running browser behavior and installed-host checks when the host boundary changes; component fixtures cover only their states. | Host/version cannot be verified, required integration absent, or ownership contract changes. |
| Mobile and native platform: changed native interaction, lifecycle or platform integration. | Platform/version, app entry points, lifecycle, permissions and available simulator/device. | Use the project's platform skills/drivers; implement assigned native behavior and inspect lifecycle effects. | Named simulator/device observations; real hardware for affected capabilities the simulator cannot establish. | Missing platform access, permission choice or untested device-only requirement. |
| Performance: measured slowness or a defined timing/resource target. | Metric, baseline, representative workload, environment and budget. | Profile the bottleneck, change one supported cause, compare comparable runs. Follow [Performance](../../performance/SKILL.md). | Before/after measurements with variability and limits; user-path evidence for user-path claims. | No trustworthy baseline, changed workload, regression or unresolved resource tradeoff. |
| Backend and data: changed schema, validation, persistence, concurrency or integration contract. | Consumers, schema/ownership, migration needs, permissions and deployment target. | Trace indirect consumers; edit only under assigned ownership; use [Convex guidance](database.md) and its companion expert/reviewer when applicable. | Actual validation, permitted/denied data operations, persistence and concurrency cases when affected; consumer compatibility. | Data loss risk, unresolved migration/ownership choice, unavailable required Convex review or wrong environment. |
| Delivery review: change is ready for assessment, with an independent pass when breadth/risk warrants it or policy requires it. | Original assignment, acceptance, full diff, proof records, project standards and pinned revision. | Inspect intent and quality separately using [PR guidance](../../pr/SKILL.md); report actionable findings as a read-only reviewer. | Findings grounded in code or observations, including proof gaps and indirect consumers. | Required proof absent, unresolved material findings or unavailable mandated review; keep the result partial/draft. |

## Resolve contributions

Each report names role, actor, independence, scope, exact reviewed/delivered revision, environment, findings, proof and gaps using the [contribution contract](handoffs.md#specialist-contribution). Findings have stable IDs and link a concrete case or risk; distinguish candidate concerns from reproduced defects.

The lead records each material finding as fixed with recheck, not confirmed with evidence, accepted limitation with owner authority, or open with owner/next action. Advisory recommendations can be declined with a reason. A confirmed defect affecting acceptance keeps the work incomplete until fixed or explicitly accepted by the owner. Recheck evidence after relevant changes; a review of an earlier revision cannot clear a later affected diff. Consolidate the contributions into one result without hiding disagreement, missing independence or proof gaps.
