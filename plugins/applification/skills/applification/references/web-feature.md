# Web feature design sprint

Use as the opening design sprint for every feature that adds or changes a web UI, including a small visible change. Pencil and Storybook are required. Keep the pass small when the change is small; do not omit either tool because the result seems obvious. A feature with no web UI does not need these artifacts.

## Choose the stack

Keep an existing project's framework unless the feature itself warrants migration. In a clean repository, use the [Bun and Turborepo layout](project-setup.md). Put the web app in `apps/web` and reusable UI in `packages/ui`, using **shadcn/ui and Tailwind CSS**. Start every new web product with **Next.js App Router + TypeScript**, including client-heavy products. Consult the current [shadcn monorepo](https://ui.shadcn.com/docs/monorepo) and [Next.js](https://nextjs.org/docs/app/getting-started/installation) setup guides rather than assuming old scaffold flags. Use Bun for dependencies and scripts, and [Portless](project-setup.md) for local web startup.

Needing a database does not require an extra web framework decision. Use [Convex](database.md) with Next.js in a new web product; retain the framework of an existing app unless migration is requested.

Set up Storybook in the chosen application before implementing the feature UI, including stories for shared components from `packages/ui`. Use the current official [Next.js/Vite](https://storybook.js.org/docs/get-started/frameworks/nextjs-vite) integration for a new app and confirm that Storybook starts. Configure [shadcn lint](shadcn-lint.md) for the app, shared UI consumers, and stories so edits get fast feedback. Do not migrate an existing project only to satisfy this default stack rule.

Use the version-matched Next.js docs as the authority for framework APIs. For focused React and UI review, [Vercel Labs agent skills](https://github.com/vercel-labs/agent-skills) can add `react-best-practices` for data flow and performance, `composition-patterns` for shared component APIs, and `web-design-guidelines` for accessibility and interaction. Apply the skill that matches the change if it is installed; do not add the whole collection as a setup prerequisite or substitute a checklist for a running user-path check.

## Design sprint into behavior contract

1. Start `.astack/<feature>/behavior-contract.md` with the actor, problem, intended outcome, material interaction states, and open product choices, following the [behavior contract](behavior-contract.md). For a substantial change, draft acceptance cases with stable IDs. Keep this as the working contract through design, implementation, and validation.
2. Create or update a `.pen` file in the same feature folder with Pencil's design tools. Keep supporting image and font assets with it. Read Pencil's own tool guidance before editing; `.pen` files are not plain text and must not be inspected or changed with shell text tools. Show the consequential states, including empty, loading, error, or confirmation only when they matter to the feature.
3. Build the presentation components in Storybook using fixture data through props. Add stories for the designed states and interactions. Run the UI lint check on changed app and story files as they are saved, and resolve new findings before comparing the story with Pencil. Keep these components suitable for production, while treating mocked requests and local placeholder state as prototypes.
4. Load the Storybook story in Pencil's browser, compare it with the design, and correct visible differences. Verify the story renders and its material interaction works. Record the chosen `.pen` frames and Storybook story IDs beside the contract cases they support, with the observed result and any gap. Resolve product or taste choices with the user when the available context cannot settle them.
5. Use the resulting contract for implementation. Trace the real data and ownership path, keep suitable presentation components, and replace prototype data flows with actual state, authorization, and persistence behavior. Select checks from its acceptance cases and add the running-app proof results to the same contract. Put evidence worth retaining in `.astack/<feature>/evidence/`; keep disposable captures outside the repository.

The sprint hands off one tracked `.astack/<feature>/` folder for implementation and validation. Its contract connects the `.pen` design, Storybook stories, and running-product evidence. Link that contract from the feature PR. If Pencil or Storybook is unavailable, state the concrete blocker and continue independent work; a draft PR may preserve progress, but the web feature is not complete until the required design and component checks run or the user explicitly changes the requirement.
